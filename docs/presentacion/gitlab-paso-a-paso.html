1. Iniciar sesión en GitLab con la cuenta de GitHub

1

Entra en https://gitlab.com/users/sign_in y pulsa Sign in with GitHub (o Register → GitHub si es la primera vez).

2

GitHub pide autorizar a GitLab: Authorize GitLab. GitLab crea la cuenta con el mismo usuario (Nicollflorez).

3

Completa el formulario de bienvenida (rol, uso) y confirma el correo si lo pide.

4

Verificación de la cuenta: para usar los runners gratuitos de gitlab.com hay que validar la identidad (teléfono o tarjeta, sin cobro). Sin esto, el primer pipeline queda en failed sin jobs.

Lo vivimos: los dos primeros pipelines fallaron con "0 jobs" hasta validar la cuenta. Después, un pipeline nuevo ya creó sus 7 jobs.

3. Subir el código desde el PC

El proyecto ya estaba en Git (y en GitHub). Solo se agrega GitLab como segundo remoto:

# en la carpeta del proyecto
git remote add gitlab https://gitlab.com/Nicollflorez/smartbody.git
git push -u gitlab main

Al hacer push por HTTPS, el Git Credential Manager de Windows abre una ventana para iniciar sesión en GitLab (con GitHub). Se hace una sola vez.

Si dejaste marcado "README", el push se rechaza (non-fast-forward). Solución sin forzar: git merge gitlab/main --allow-unrelated-histories y volver a hacer push.

Detalles que importan en Windows

  • .gitattributes fuerza LF en mvnw, gradlew y *.sh: los runners son Linux.
  • El bit de ejecución no existe en Windows: git update-index --chmod=+x backend/mvnw android/gradlew. Sin esto el job falla con Permission denied.
  • Nunca se suben claves ni contraseñas: backend/keys/, *.pem, .env están en .gitignore.

4. Runners: quién ejecuta el pipeline

Un runner es la máquina que corre cada job. gitlab.com ofrece instance runners compartidos (Linux, 2 vCPU) gratis para proyectos públicos.

1

Settings → CI/CD → Runners.

2

Interruptor "Enable instance runners for this project" activado; debajo se listan los runners Online.

3

Un job sin etiqueta (tags) cae en el runner Linux pequeño; algunos usan Docker-in-Docker (services: docker:dind) para crear contenedores dentro del job.

La primera vez el job puede quedar pending 10-15 min: es cola de runners gratuitos, no un error (ver captura "Este trabajo aún no ha empezado").

5. El pipeline se define en .gitlab-ci.yml (raíz del repo)

# Opciones del formulario "Run pipeline"
spec:
  inputs:
    publicar_release: { type: boolean, default: false }
    version_release:  { type: string,  default: "" }
---
stages: [version, build, test, package, docker, deploy, publish, release]

variables:
  PUBLICAR_RELEASE: "$[[ inputs.publicar_release ]]"
  MVN: "./mvnw -B -ntp"

workflow:            # cuándo se crea un pipeline
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == "main"

build:backend:      # un job
  stage: build
  image: eclipse-temurin:17-jdk
  needs: [version]
  script:
    - cd backend
    - $MVN -DskipTests compile

Conceptos

  • stage: fase ordenada. job: unidad que corre en un runner.
  • image: contenedor Docker donde corre el job (JDK, Android SDK, Kaniko, kubectl…).
  • script: comandos; si uno falla, el job falla.
  • needs: dependencias reales (DAG): el job arranca en cuanto sus needs terminan, sin esperar toda la fase.
  • artifacts: archivos que pasan a jobs siguientes (jar, apk) y reports: junit alimenta la pestaña Tests.
  • cache: .m2 y .gradle para no descargar dependencias cada vez.
  • rules / when: manual: condiciones y botón de aprobación.
  • spec:inputs: campos del formulario Run pipeline (la interfaz nueva ya no muestra variables).

7. Primera ejecución y cómo leerla

1

Cada git push a main crea un pipeline: Build → Pipelines.

2

Entra al pipeline: el grafo muestra las fases y el estado de cada job (azul: corriendo, verde: ok, rojo: fallo, gris: en espera).

4

Pestaña Tests: suites JUnit con pasadas/fallidas por job.

5

Botón Download (artefactos) y Retry por job.

8. Repositorio de artefactos: Package Registry

Cumple el rol de Nexus/Artifactory sin instalar nada: un repositorio Maven propio del proyecto. Cada compilación que pasa las pruebas deja el jar y el apk versionados.

# job publish (.gitlab-ci.yml)
$MVN -s ../devops/maven/settings.xml deploy:deploy-file
  -DrepositoryId=gitlab
  -Durl=$CI_API_V4_URL/projects/$CI_PROJECT_ID/packages/maven
  -DpomFile=pom.xml -Dfile=target/smartbody-backend-$VERSION.jar
# devops/maven/settings.xml: autenticación con el token del job
<server><id>gitlab</id>
  <configuration><httpHeaders><property>
    <name>Job-Token</name><value>${env.CI_JOB_TOKEN}</value>
  </property></httpHeaders></configuration>
</server>

Dónde verlo

Deploy → Package Registry: com/smartbody/smartbody-backend y smartbody-android, versiones 1.0.x-SNAPSHOT (desarrollo, se sobreescriben) y 1.0.1 … 1.0.4 (oficiales).

Claves

  • CI_JOB_TOKEN lo crea GitLab para cada job: no hay que guardar contraseñas.
  • Se publica el mismo jar que pasó las pruebas (artefacto), nunca se recompila: promoción de artefactos.
  • La versión vive en un solo sitio: backend/pom.xml; el pipeline la propaga al APK.

9. Lanzar una versión oficial (Run pipeline + aprobación)

1

Build → Pipelines → New pipeline, rama main.

2

En Inputs: publicar_release = true; version_release vacía (usa la del pom sin -SNAPSHOT) o una concreta; api_base_url = URL real del servidor para el APK.

3

New pipeline. Corre build, test, package, docker, deploy… y se detiene en publish:release con un botón ▶: esa es la aprobación del lanzamiento.

4

Al pulsar ▶: publica jar y apk oficiales; el job release crea el commit Release vX.Y.Z, el tag, el commit X.Y.Z+1-SNAPSHOT y el Release en Deploy → Releases.

10. Variables de CI/CD: dónde viven los secretos

1

Settings → CI/CD → Variables → Add variable.

2

Key GITLAB_PUSH_TOKEN, Value el token, Masked (nunca aparece en logs), Protect desmarcado, Environments: All.

3

En el job se usa como variable de entorno: $GITLAB_PUSH_TOKEN. Si no existe, el job release salta el commit de versión (lo avisa en el log).

Variables que GitLab ya da

  • CI_JOB_TOKEN: Package/Container Registry.
  • CI_REGISTRY, CI_REGISTRY_USER, CI_REGISTRY_PASSWORD, CI_REGISTRY_IMAGE: Kaniko.
  • CI_COMMIT_BRANCH, CI_COMMIT_SHA, CI_PIPELINE_IID, CI_PROJECT_ID, CI_API_V4_URL.
Un valor pegado en un chat, un log o un commit ya no es secreto: revócalo y crea otro.

12. Imágenes Docker: Container Registry con Kaniko

docker:servicios:
  stage: docker
  image: { name: gcr.io/kaniko-project/executor:v1.23.2-debug, entrypoint: [""] }
  needs: [version, package:servicios]
  retry: 2
  parallel:
    matrix:
      - SERVICIO: [auth, planes, progreso, admin]
  script:
    - echo "{\"auths\":{\"$CI_REGISTRY\":{\"auth\":\"$(printf %s:%s $CI_REGISTRY_USER $CI_REGISTRY_PASSWORD | base64)\"}}}" > /kaniko/.docker/config.json
    - /kaniko/executor --context $CI_PROJECT_DIR/services
        --dockerfile $CI_PROJECT_DIR/services/Dockerfile
        --build-arg SERVICIO=$SERVICIO --build-arg VERSION=$VERSION
        --destination $CI_REGISTRY_IMAGE/$SERVICIO:$VERSION
  • Kaniko construye imágenes sin demonio Docker (los runners compartidos no lo permiten directamente).
  • parallel: matrix crea 4 jobs a la vez, uno por servicio.
  • retry: 2 repite el job si falla por algo transitorio (red, registro).
  • Las imágenes quedan en Deploy → Container Registry: backend, auth, planes, progreso, admin, con tags 1.0.x-SNAPSHOT, 1.0.4 y latest (solo desde main).
  • Se construyen desde el jar probado (artefacto), no desde el código.

13. Ramas y Merge Requests

Los cambios grandes (Etapas 6-8, pruebas e2e, microservicios) se hicieron en ramas para no tocar main hasta tener el pipeline en verde.

git checkout -b etapa-6-7-8
# ... cambios y commits ...
git push -u gitlab etapa-6-7-8 \
  -o merge_request.create \
  -o merge_request.target=main \
  -o merge_request.title="Etapas 6 y 7"
  • Las push options crean el Merge Request desde la terminal.
  • El MR tiene su propio pipeline (merge_request_event): valida antes de integrar.
  • Al estar en verde: Merge (o git merge --ff-only y push a main).

Lo que hicimos

MRContenidoResultado
!1Docker, Kubernetes, Nginx, Prometheus/Grafana3 iteraciones (YAML, kind con dind) → verde
!2Pruebas end-to-end de la API (Postman/Newman)verde a la primera
!34 microservicios + gateway3 iteraciones (Kaniko transitorio, CPU de MySQL) → verde
Regla: nada entra a main con el pipeline en rojo.

14. Despliegue de prueba en Kubernetes dentro del pipeline

k8s:kind:
  image: docker:27
  services: [docker:27-dind]          # Docker-in-Docker
  script:
    - kind create cluster --name smartbody --config k8s/ci/kind.yaml
    - kubectl config set-cluster kind-smartbody --server=https://docker:$PUERTO --insecure-skip-tls-verify=true
    - BACKEND_IMAGE=$CI_REGISTRY_IMAGE/backend:$VERSION sh k8s/desplegar.sh
    - curl -sf http://docker:30080/api/ping
    - newman run tests/e2e/smartbody.postman_collection.json
        --env-var baseUrl=http://docker:30080 --reporters cli,junit
  after_script:                           # diagnóstico aunque falle
    - kubectl -n smartbody get pods -o wide
    - kubectl -n smartbody get events | tail -25
    - kind delete cluster --name smartbody
  • kind crea un clúster Kubernetes real dentro del runner en ~2 min.
  • Se despliegan MySQL, backend (o los 4 servicios), Nginx, Prometheus y Grafana con los manifiestos de k8s/.
  • Newman ejecuta la colección Postman: 21 peticiones, 36 aserciones, reporte en Tests.
  • Mismo criterio para monolito y microservicios: la misma colección debe pasar en ambos.
  • El clúster se destruye al terminar: cada ejecución parte de cero.

16. Mantenimiento diario del pipeline

Evitar ejecuciones inútiles

Un cambio solo de documentación no necesita 25 minutos de pipeline:

git push -o ci.skip gitlab main

GitLab registra un pipeline Skipped (gris): no es un error.

Reintentar

  • Botón Retry en el job (misma configuración).
  • retry: 2 en jobs con fallos transitorios (Kaniko).
  • Un pipeline nuevo si cambió .gitlab-ci.yml: el retry usa la versión vieja.

Limpiar el historial

  • Abrir el pipeline → icono de papelera → Delete pipeline.
  • Por API con un token api: devops/gitlab/limpiar-pipelines.sh borra failed/skipped/canceled y conserva los verdes.

Leer un fallo rápido

  1. Pipeline rojo → job rojo → final del log.
  2. Buscar ERROR, Caused by, exit code.
  3. En kind: el after_script ya imprime pods, eventos y logs.
Hoy: 11 pipelines, todos en verde.
